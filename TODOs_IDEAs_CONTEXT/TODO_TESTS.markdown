## 2. AUTHN & AUTHZ Test Coverage Audit

### What is Tested:
* **`UsersRequestSpec`**: Verifies that guests can view `index` / `show` and register via `create`, but are forbidden (`403`) from editing or deleting other users.
* **`UserPolicySpec`, `MemberPolicySpec`, `CurrentTeamPolicySpec`**: Unit tests verifying basic policy rules (`guest user`, `current_team_scope`, owner permissions) using shared examples.
* **`JobDashboardRequestSpec`**: Confirms that non-admin users cannot access `/admin/jobs` (MissionControl).

### Critical AUTHN & AUTHZ Gaps:
1. **Role Sampling Intent**:
   - `CurrentTeams::` request specs and policy specs intentionally use `roles.sample` across permitted roles (e.g. `%i[owner manager editor]`) to test representative role permissions without incurring the execution time of testing every single role permutation on every run.
   - Complementary negative specs can specifically assert boundary rejections (e.g., verifying that a `reader` is strictly denied write actions).
2. **Multi-Tenant Isolation Leakage Tests are Missing**:
   - No request specs test cross-team data access (e.g. Team A authenticated user directly requesting `/current_team/locations/:id` belonging to Team B).
3. **Session Expiry & Device Tracking Not Verified**:
   - Pruning of older sessions (`NUMBER_OF_LOGIN_SESSIONS_TO_KEEP = 3`) and device invalidation via `logout_if_login_record_has_been_deleted` have no request or integration specs.

### D. System & Integration Layer
* **Zero System Tests**:
  - No end-to-end browser specs testing Turbo navigation, Stimulus controllers, or full user flows (Sign in ➔ Switch Team ➔ Create Memory ➔ View Map).

## 4. Critique of Test Style & Conventions

### 1. 💡 The `roles.sample` Pattern & Performance Strategy
* **The Pattern**:
  ```ruby
  # In spec/policies/location_policy_spec.rb & spec/requests/current_teams/
  let(:roles) { %i[owner manager editor] }
  before do
    Member.create!(team: team, user: user, roles: Array(roles.sample))
  end
  ```
* **Rationale & Value**:
  - **Performance Optimization**: As the number of roles grows (`owner`, `manager`, `editor`, `publisher`, `reader`, `guest`), running every test example against every permutation adds significant execution overhead. Sampling a representative role from the permitted set keeps the test suite fast (~11s for 320+ specs).
  - **Catching True Regressions**: If a sampled role fails, it indicates an actual defect (e.g. an invalid role configured in `VALID_ROLES`, or an unintended permission revocation).
  - **General Capability Testing**: Ideal for actions where any authorized team member should have equal access (e.g. viewing team content, creating draft memories).
* **Best Practice**:
  - Ensure `roles` is passed as a valid Array of candidate roles (e.g. `%i[owner manager editor]`) so `.sample` picks from valid options.
  - Complement with focused, deterministic negative specs for unauthorized roles (`reader` attempting create/update/destroy).

### 2. ⚠️ Over-Reliance on Boilerplate Scaffold Comments
* **The Pattern**: Every request spec begins with 12 lines of generic Rails scaffold generator comments.
* **Critique**: Adds noise and clutter. Remove boilerplate and replace with concise spec descriptions.

### 3. ⚠️ Monolithic Request Specs vs Focused Contexts
* **The Pattern**: Scaffold specs test `GET /index`, `POST /create`, `DELETE /destroy` in a single flat file without structuring tests around user personas (Guest vs Member vs Owner vs Cross-Team Attacker).
* **Fix**: Organize specs with standard RSpec contexts (`context "when unauthenticated"`, `context "when member of another team"`, `context "when team owner"`).
